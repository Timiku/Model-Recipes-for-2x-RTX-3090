# vllm-56531-spec-row-classification

**Source:** vLLM PR [#56531](https://github.com/vllm-project/vllm/pull/56531) — "[Bugfix] Route every speculation-capable row through the speculative path so recurrent state stays consistent" (@vadiklyutiy). **OPEN** (not merged) as of 2026-09-13. Vendored, NOT hand-rolled; upstream provenance kept in file contents.

**Root cause (the PR's #40875 + the prefill-tail analysis):** in the hybrid GDN/Mamba recurrent path, a row that *could* draft but drafted *nothing* this step was classified as a plain decode row and took the non-speculative path. The recurrent state of a speculative row lives at an accepted-token offset that the plain decode path never applies, so such a step reads the state inconsistently. Two stock-code hazards the PR also fixes: (a) `num_accepted_tokens` buffers init to zero, and dummy/profiling runs skip `_prepare_inputs`, so a `0` reaches the kernels as slot index `-1` — an out-of-bounds read; (b) the prefill tail (a one-token chunked-prefill continuation) is indistinguishable from a zero-draft decode row by token count alone — the PR's own earlier revision crashed Kimi-Linear with an **illegal memory access** by misclassifying it.

**Why we carry it:** on the Qwen3.8-27B MTP tier (Qwen3.5 GDN hybrid, sm_86, TP=2, 262k window, chunked prefill 4096) the nightly `0.29.1rc1.dev9+g2671fedfc` faults with a CUDA illegal memory access at the **end of every long chunked prefill** (~34-44 s into a fresh 120k-token prefill, ~300 s into a 210k resume-extend), on FlashInfer fp8-KV and FA2 bf16 alike, runner-independent on V1's resume leg, and in the Triton/FLA GDN prefill backend (the only backend Ampere gets — flashinfer GDN needs SM90+, cutedsl SM100). The fault-vs-size and end-of-prefill-timing signatures match the misclassified prefill-tail / zero-draft-row hazards this PR fixes; the upstream text documents stock-code IMAs from exactly these two hazards. The PR is the *fix in flight*; it is not yet in any release image, so we vendor and carry it until it merges.

**Re-anchor notes (0.29.1rc1.dev9+g2671fedfc):**
- `gdn_attn.py` build() block: verbatim anchor, verified.
- `mamba_hybrid.py`: `prepare_attn` stock block verbatim; `compute_num_decode_draft_tokens` inserted before `MambaHybridModelState`; the runner's `num_decode_draft_tokens` loop already carries the `num_scheduled_tokens == draft_len + 1` guard on this base (main evolved past the PR's base), so the zero-draft mask inserts after it.
- One adaptation beyond verbatim: `zero_draft_decode_mask` uses `InputBatch.is_prefilling_np` (this base's field) where the PR's base read `num_computed_tokens_cpu >= num_prompt_tokens` — per the PR's own prose, the V2 equivalent is the is_prefilling flag.

**V1/V2 compat (v3 patch):** `prepare_attn` reads `is_prefilling_np` defensively (`getattr`, dummy on the V1 InputBatch) and the runner-side zero-draft promotion is skipped when the field is absent (V1's stock exclusion is already correct per the PR). Both runners boot with this bundle.

**Status (2026-09-14, final):** the bundle is CORRECT and carried, but it does NOT stop this box's large-prefill IMA. A/B on the nightly (`0.29.1rc1.dev9+g2671fedfc`, all 8 bundles): MRV2+mtp A-seed (fresh 120k prefill) still IMA'd (52.8 s), and after the v3 V1-compat fix MRV1+mtp also IMA'd (30.2 s) — the fault is neither the spec-row classification family nor the mamba-bounds family. The faulting kernel remains unnamed (coredump: no CUDA focus on WSL2/paravisor, twice; memcheck: NCCL instrumentation artifacts + instrumentation-OOM). Keep the bundle as correctness armor for the zero-draft/prefill-tail state-corruption class; do NOT re-run memcheck/coredump on this box expecting a kernel name. Adoption into the canonical `mtp.yml` is blocked pending direction (cap / wait for upstream / a native-Linux host where compute-sanitizer works).
