# vllm-kvarn-0290 — KVarN int4 KV cache on stock vLLM 0.29.0

KVarN ([huawei-csl/KVarN](https://github.com/huawei-csl/KVarN), Apache-2.0, [arXiv 2606.03458](https://arxiv.org/abs/2606.03458)): a native vLLM KV-cache quantization backend. 4-bit keys / 2-bit values per 128-token tile, Hadamard rotation + iterative variance normalization (Sinkhorn), per-tile scales, a small fp16 outlier/sink pool. Triton kernels, JIT-compiled: sm_86-native, no FP8/FP4 tensor cores needed. `--kv-cache-dtype kvarn_k4v2_g128` + `--block-size 128` (one vLLM block = one KVarN tile).

## House adaptations (ours, listed for the next rebase)

0. **The `mamba_hybrid.py` hunk is dropped.** It fixes the same bug as our own `vllm-mamba-align-seed` bundle (#53142: seed the align pre-copy's running state index with the *mamba* block size, not the KV block size) at the same line, and our bundle is already applied and boot-validated on this box. The port's version resolves the block size from `self._mamba_spec`, ours from the runner's `kv_cache_config` — ours also covers the first `add_request`, which precedes `preprocess_state`. Keeping both is a hard conflict at the same hunk (that is what refused the first boot on 09-14); `install.sh`'s drift guard caught it, which is the guard working.

1. `install.sh` rewritten to the container contract: fixed mount `/etc/vllm-patches/kvarn`, `VLLM=/usr/local/lib/python3.12/dist-packages/vllm`, idempotency guard on the `kvarn_k4v2_g128` literal, `--fuzz 0` on both patches, a marker-count check and an import check; any failure exits 1 so the tier refuses the boot. Upstream's venv-python discovery is dropped (no venv in the image; `python3` is the image's interpreter).
2. The v2-runner patch is split stock/dflash2 (above). Upstream applied both; we apply the stock five and park the drafter pair.
3. **`files/.../kvarn_attn.py` carries a local diagnostic delta** (09-15): `KVARN_BT_DEBUG=1` makes `KVarNMetadataBuilder.build` validate every block id it is about to hand to the decode kernels — per request, the count in the read range, the id min/max, any negative id, any id ≥ the int4 cache's block count, and the per-request block count vs the block-table row width — plus `total_k` vs the FA scratch rows (`over_scratch=yes` states the fact; the route itself is printed by the path, see #4). `forward()`/`do_kv_cache_update` also stash the true cache block count on the class for that check. Off by default; one `print` per step. It exists because an illegal memory access in the decode path had to be told apart from a bad block id (it was not one: 1,760 instrumented steps over 16 long-context levels, every id valid). Re-apply after any re-vendor of the port.
4. **`files/.../kvarn_attn.py`: an over-cap batch stays on the fast path** (09-15). The FA scratch holds ONE packed write of `fa_scratch_rows` tokens (262,144 when `max_model_len` is 262,144) and `_cached_multiquery_path` packs the whole batch into it as a single varlen run, so a batch summing past that was routed to `_decode_path_slow`, whose fp32 materialize asks for ~3 GiB beside a full cache. Measured on 2×260k (summed 263,873): `Tried to allocate 2.98 GiB`, both ranks, two boots. The path now splits the batch into greedy **scratch-fitted request groups** and runs the SAME packed-kv kernel and the SAME `flash_attn_varlen` call once per group; each group's rows, `cu_k` and `cu_q` are re-based to local index 0 and the scratch is reused from its start. Numerics are untouched: FlashAttention tiles each sequence independently, so a group boundary cannot change a sequence's result. This is the port's own Phase-2 "segmented materialize", implemented by request instead of by key axis; the partition is `_scratch_groups`, and `KVARN_BT_DEBUG=1` prints the chosen grouping as `[KVARN_MTQ]` lines (every multi-group call, plus a 50-call sample of the common path: this path runs once per layer, so a flat cap used to swallow the interesting lines about fourteen prefill chunks into a 260k run).

   **The under-cap case is byte-for-byte the pre-change call.** One group, if it spans the whole batch, calls the kernel and `flash_attn_varlen` with the same tensors, the same offsets and the same arguments as before, and uses the returned tensor directly — no `empty_like`, no scatter-copy, no extra host sync (the host copy of `seq_lens` replaces the old `int(cu_k[-1].item())`, so the path keeps exactly one D2H sync). It has to be that way: a wild access in a compiled inductor piece turned out to be reachable at all in this family, and the allocator layout this path leaves behind is one of the things that decides whether it fires. Measured A/B, one boot per arm, same session: unpatched 235.7 s and byte-identical 235.9 s on 1×260k, needle 1/1 both.
 Validated on the shipped build: 2×260k 638.7 s, needles 2/2, **0 faults** (the exact OOM step `B=2 total_k=263873 over_scratch=yes` now runs through); 1×260k 330.1 s needle 1/1; 4×65k 239.0 s needles 4/4; positive control 2/2 at 4k. Numerics: an A/B in one session on a frozen eval text gives **identical** numbers on both builds (8008 tokens, mean NLL -1.674445, PPL 5.335835). The slow path is now only for `head_dim > 256` and for a single request wider than the scratch. A rebase re-applies the routing; nothing needs re-tuning, but run `qwen3.8-27b/vllm/scripts/test-scratch-groups.py` after one — it extracts the helper from this file and checks the partition contract, which is the piece of local logic a rebase can silently drop. Two route markers, both under `KVARN_BT_DEBUG=1`: `[KVARN_MTQ]` prints the grouping on every multi-group call plus a 50-call sample of the common path, and `[KVARN_SLOW]` marks every entry to the fp32 fallback with its summed context and the scratch size — a `[KVARN_SLOW]` line whose sum exceeds the scratch means the fast path declined a batch it could have taken.

5. **`files/.../kvarn_attn.py`: the head-512 SDPA paths stay on a fused backend** (09-16, gemma-4). `F.scaled_dot_product_attention` with `enable_gqa=True` at mismatched head counts has exactly one backend left — math — which materializes the full q x k score matrix in fp32: 1 GiB for gemma's first 4096-token chunk (Hq=16/rank, head 512; the "Tried to allocate 1024.00 MiB" OOM, and ~26 GB per continuation chunk at ctx 100k). `_sdpa_grouped` groups the q heads per kv head and broadcasts K/V (stride-0 expand, same head mapping as `enable_gqa`), which keeps the mem-efficient kernel engaged: probed in the v0.29.0 container on sm_86, q=4096 x ctx=189000 head 512 is +128 MiB maskless/is_causal and +1.6 GiB with a bool mask, vs +2.9 GiB for math at q=k=4096. Both SDPA call sites (`_prefill_first_chunk`'s fallback and `_decode_path_slow`) route through it, and `_decode_path_slow` drops its `.float()` upcast (fp16 end to end; the upcast doubled the gather to 1.55 GiB at ctx 189000). Tier-side fit: the bool-mask path's peak scales with the chunk, so the gemma kvarn tiers pin `MAX_NUM_BATCHED_TOKENS=1024` in their machine configs (~0.5 GiB headroom at ctx 189000). A rebase re-applies the helper; the shape probes live in `.boxpatch/boxprobe/sdpa{,2,3}-probe*.py`.

   **#5b (09-16, later the same day): the masked path streams.** The mem-efficient kernel still converts a bool mask into an internal bias whose size scales with query x context — 514-824 MiB at the deep tail of a 189k prefill, an OOM no utilization could absorb. `_sdpa_streaming` (called from `_decode_path_slow` instead of the masked `_sdpa_grouped`) runs flash attention's streaming softmax over fixed K/V blocks, so the peak is constant in context. CPU check (`.boxpatch/boxprobe/stream-check.py`, S=9000, 3 blocks): max abs diff 3.4e-08 vs the masked-SDPA reference.

   **#5b v2 (09-16, hours later): the loop goes allocation-free.** The first version allocated ~0.5 GiB of fresh fp32 tensors per block; at deep context (~165k, the deepest sustained run this backend had ever done) the churn pushed the WDDM shared-memory commit pool to its ceiling and GPU-PV surfaced it as `cudaErrorNotReady` — the WSL kernel log showed `dxgkio_make_resident: Ioctl failed: -12` at the failure second, no Xid, no TDR, no nvlddmkm event. v2 allocates every buffer once per call and reuses it in place across blocks (scores, K/V blocks, PV out, the running-max/alpha scalars); the CPU check is unchanged at 3.4e-08.

   **#6 (09-17): the slow path works in the rotated frame.** The old `_gather_request_kv` loop dequantized AND un-rotated per block with a GPU-to-CPU `.item()` sync per block (~1400 blocks x 10 layers per decode token at 180k: the bulk of the 3.3 s/token tax) plus a 1400-part `torch.cat`. Now the gather returns the pool/cache's own rotated fp16 frame with ONE `.tolist()` sync and no per-block Hadamard; the caller (`_decode_path_slow`) rotates q in and un-rotates the output with the same fp16 Sylvester H the store side uses — the fast decode path's own convention, so QK^T is invariant and the math is exact. Needle-gated: HIT 20k/100k; walls 54.0 -> 45.5 s at 20k (-16%) and 892.7 -> 830.7 s at 100k (-7%). The rest of the gap — the per-block dequant launches plus the fp16 intermediate traffic — is what #7 and (later) #8 close.

   **#7 (09-17): the gather is the fast path's own kernel.** The slow path's per-block python loop (~781 iterations x 10 layers per chunk at 100k, each a tiny Triton dequant launch — the measured bulk of the 830.7 s wall) is replaced by ONE `_kvarn_build_packed_kv_kernel` launch per request: the exact kernel the fast path packs its FA scratch with every step, same constexpr set as the warmup compiles, pool slots and bit-width-aware dequant and the masked partial tail handled inside. Fixed-address per-request scalars (`sl_one`/`cu_k`) keep every launch's pointer alignment identical so Triton serves ONE compiled variant. The old `_gather_request_kv` + `_read_block_dequantized_rotated` are gone (the CPU reference lives on in the probe). Gates: `gather-check.py` (GPU, container-composed like the boot's patch-apply): pool copies and packed dequant BIT-EQUAL to the pre-#7 ops path on both bit widths, tail masked, nothing past seq_len. Needle at 0.93: 20k 45.5 -> **29.6 s** (-35%), 100k 830.7 -> **327.9 s** (-61%), 180k **HIT** (1273.9 s, prefix-warm mix); pool unchanged 404,811 / 2.14x, fault scan 0. The remaining depth cost is the fp16 intermediate traffic (~2.6 TiB per 100k needle) — that is candidate #8's target (packed-direct streaming, the online-cache-quantization pattern), still designed-not-started in the plan doc Phase 5. [The #8 prototype corrected this premise: the 2.6 TiB is ~1% of the wall; the wall is the streaming loop's per-block Python overhead. See #8a.]

   **#8a (09-21): the streaming loop goes fat and fp16.** The #5b v2 body's per-block cost model was wrong twice over: the fp32-intermediate traffic is ~3.6 s of a 327.9 s wall (~1%), and the real cost is the Python loop's per-block overhead — ~14 kernel launches per BLK-key iteration, with the guard halving BLK to 1024 at Lq=4096 (~98 iterations per 100k chunk-layer). The prototype (`.boxpatch/boxprobe/kvarn-prefill-probe.py`, deployment container, LQ=1024 ctx=100k history-only, D=512) measured the candidates: fused packed-direct kernel 144.6 ms/layer-chunk (SMEM-capped at 32 q-rows), gather+grouped-SDPA 285 ms (dead — mem-efficient at head 512 runs ~8 TFLOPS), **gather+batched-streaming 117.7 ms** — the winner with no new kernel. #8a re-blocks `_sdpa_streaming` into that shape: grouped q `[Hk, R2, D]` fp16 pre-scaled, one fp16 tensor-core bmm per 4096-key slice (slice budget: 512 MiB of score-shaped buffers, which reproduces the probed configuration at Lq=1024), fp32 running max/sum/acc (the #5b accumulator discipline), exp in fp32, p cast to fp16 only for the PV bmm, every buffer allocated once per call (#5b v2 flat-buffer rule). The one real precision delta vs the old body: scores round to fp16 at the bmm output before the max/exp. Box check (`.boxpatch/boxprobe/kvarn-bstream-check.py`, deployment container, old body vs new on identical random states, D=512 Hq=16 Hk=4): needle-chunk Lq=1024 S=100k max abs 1.9e-6 / max rel 1.9e-3, decode Lq=1 S=100k same class, chunk-4096 and a straddling case ≤ 8.1e-3 on the 1e-3-floored rel, 0 NaN/Inf everywhere; medians old→new: 176→97.5 ms (needle chunk), 32.6→10.7 ms (decode step, 3.0x), 260→168.4 ms (Lq=2500). Returns token-major `[B1, Lq, Hq, D]` now — the caller's un-rotation is one contiguous reshape. The fused direct kernel and its bit-clean numerics template stay in the probe as the validated next lever (D-half score accumulation to fit R=64) if the tier numbers disappoint. Tier gates (09-21, boot 8105): install.sh marker+import clean, needle ladder 3/3 HIT, 20k 28.8 s / 100k 255.2 s (was 327.9) / 180k 899.3 s (was 1273.9), fault scan 0.

   **#8b (09-21): the slow path's gather output stops churning.** The bench's full-depth rows under #8a read TTFT 251 s (the prefill win, real) but decode still 0.4 tok/s at 100k — with the streaming and gather math itself at ~26 ms/layer-step (~0.3 s of the 2.4 s token). The rest was allocation: `_decode_path_slow` built seq_len x Hk x D fp16 K_rot/V_rot fresh every layer every token — ~8.2 GiB of per-step alloc/free on the WDDM GPU-PV box, the same pattern the #5b v2 rewrite fixed for the streaming loop (dxgkio_make_resident -ENOMEM class). #8b pools them: class-shared per (device, D, Hk) like the FA scratch, grown in 4096-token steps to the largest context seen, sliced per request (stream-ordered serial use: one request's gather completes before the next overwrites). Eager-only path, so persistent buffers are safe; costs ~0.8 GiB resident at the 100k row (the old transient peak, held instead of cycled).

   **#8b-diag + #8d (09-21): the decode step goes packed-direct.** #8a and #8b transformed the prefill and left deep decode untouched: the bench still read 0.3 tok/s at a 100k context. The timed boot (KVARN_BT_TIMING=1, per-layer sync-bounded stage prints) named the wall: the gather stage averaged **241.5 ms/layer** and the attention 177.1 ms/layer at a 100k context — against 15.7/10.7 ms for the same code in the isolated probe. The production multiplier is the wholesale rewrite of the ~840 MB fp16 gather pool every layer every step under the box's WDDM GPU-PV residency (the #5b v2 class), which the isolated probe never sees. #8c (one grouped SDPA instead of the streaming loop at Lq=1) moved nothing — the attention was not the wall. **#8d** ports the #8 prototype's packed-direct kernel into the bundle (`ops/triton_kvarn_prefill_direct.py`): a single-query decode step reads the packed int4 cache + fp16 tail pools directly, dequantizes in register, and runs the online softmax in ONE launch — no fp16 K/V ever materializes, no gather, no pool rewrite. Warm compiled in `_warm_decode_kernels` (same constexprs as the serving launch). Sweep winner on the box (check8d.py, D=512): BM=4/BN=32/w=4/s=2 — BM=8/BN=64 does not fit the SMEM (102400 B required vs the 101376 limit). Port gate: bit-clean vs gather+grouped-SDPA on the indexing-sensitive random state (max abs 9.77e-4, max rel 7.9e-4, 0 NaN) after one port bug (the block-table row slice loads are flat-indexed; a stride-multiplied read went out of bounds). Semantics: every column ≤ seq_len is visible, which is exactly the decode shape; the tail pool is read through the same block_to_slot mapping as the gather, so freshly stored tokens stay visible. Prefill chunks keep #8a bstream (the kernel's prefill shape was the slower arm there); `_slow_kv_bufs` (#8b) serves the chunked prefill's gather only.

   **Gemma PPL baseline (09-17):** `prompt_logprobs` is unusable for gemma-4 on this build — the fp16 tier OOMs on the logprobs pass with a corrupted memory report, and the KVarN tier returns misaligned per-position values (a stock multimodal-wrapper bug, both KV dtypes; filed in the held upstream report). The A/B runs on the working sampled path instead: 120 teacher-forced positions from the model's own chat rendering (`apply_chat_template`, the `<turn|>` dialect + the empty thought channel — hand-typed `<start_of_turn>` probes are a foreign dialect, another earned scar), K sampled per arm, `logprobs: 20`. Result: top-1 accuracy 0.167 on BOTH arms (identical), NLL -4.123 (kvarn) vs -4.053 (fp16) = **+1.7%** on the shared positions — the qwen family's cost, on gemma too. Harness: `.boxpatch/boxprobe/ppl-one.sh` + `precompute-ids.sh`; the ids are in `out/ppl-ids-gemma.json`.

## Known limits (upstream + cpuchip, 3090)

- 3–5× KV capacity vs bf16, ~2× vs fp8; FP16-level accuracy (ppl +0.16%), needles correct 4k→240k.
- Decode ~20% slower than fp8 at 100k context; short-request throughput lower (the hybrid attention page is 2048 tokens vs fp8's 800). A capacity tier, not a single-stream speed tier: pair it with CUDA graphs and the drafter.
- `expandable_segments` must be OFF (`PYTORCH_CUDA_ALLOC_CONF` \= `expandable_segments:False`, the house value already).
- Hybrid models: only the full-attention layers are quantized; the GDN/mamba layers keep native state. The attention block must match the GDN page (2048 tokens on Qwen3.8) — the port patches that alignment in.
- Gemma-4 IS served by this bundle as of 09-16, on the stock `backend_per_kind` config flag (per-kind backend selection overrides the model-wide TRITON_ATTN forcing in `Gemma4Config.verify_and_update_config`): the 10 head-512 global layers run KVarN (`KVARN`), the 50 head-256 sliding layers stay native (`TRITON_ATTN`). Gemma-specific knobs: `KVARN_POW2_SLOT=1` (page-size unification at the 256/512 mixed head-dim geometry) and the #5 SDPA fit (`MAX_NUM_BATCHED_TOKENS=1024` in the tier's machine config). The full record — boot flags, measured pool, needle plan — lives in the source repo.
- Family caveat: KVarN + MTP + prefix caching corrupts `prompt_logprobs` — measure perplexity with `PREFIX_CACHE=0` or a non-MTP speculator.
